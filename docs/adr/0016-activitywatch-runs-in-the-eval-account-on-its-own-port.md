# ActivityWatch runs in the eval account on its own port, without the browser watcher

ActivityWatch is decided per eval in the eval config: an eval either includes it or does not, and when it is included every contributor's eval account runs it, so the record of what people did outside the agents is even across contributors. ActivityWatch has no accounts of its own; each macOS user account runs its own copy with its own data, so the eval account's copy is already dedicated to the eval (ADR 0008), and goodall copies everything it holds, from where the last copy ended to now, leaving filtering to the derived layer. Goodall asks it for data with credential-free requests to a local server (ADR 0011). The trap is that local ports are shared by every macOS user account on the Mac, and ActivityWatch's launcher, finding any ActivityWatch server already answering on its port, silently uses it, so two accounts on the default port 5600 would mix their data without a warning. We therefore give the eval account's copy its own port, and onboarding records the identifier that copy reports (`device_id`), which every capture and `goodall doctor` check before trusting an answer. The cost is the browser watcher: the extension always sends to port 5600 and cannot be configured, so it is not installed in an eval account. On macOS, ActivityWatch's window watcher already records the page address and title of the tab in front for Chrome-family browsers, Safari and Firefox-family browsers, so little is lost. Keeping port 5600 and requiring that no other account on the Mac runs ActivityWatch was rejected: the rule is easy to break by accident, and the mixing would only be found after it happened.

## Consequences

- The eval config gains a setting saying whether ActivityWatch is included. Local settings gain the eval account's ActivityWatch port and identifier, because both are true for one account on one machine (ADR 0009).
- Onboarding sets the port in two of ActivityWatch's own settings files, one for its server and one for its watchers, starts it when the account signs in, and says not to install the browser extension. The macOS permissions the window watcher needs are a step on the setup page.
- A different identifier stops the capture and fails `goodall doctor`, with a next step. Switching between ActivityWatch's Python and Rust servers, or deleting its data folder, changes the identifier, so the fix is to record the new one through onboarding.
- Raw copies are kept byte for byte in the log directory under `activitywatch/<capture moment>/`, never in the record repo, readable only by the account: the server's answer about itself, its list of buckets, and each bucket's events for the range copied. Each copy overlaps the previous one slightly, because ActivityWatch lengthens its newest event while the same window stays in front; readers drop the overlap. Where the last copy ended is goodall's own bookkeeping, kept outside `activitywatch/`. None of these files ends in `.jsonl`, so Scout's importer never reads them as Claude sessions (ADR 0015).
- Copies are taken at `goodall stop`, and at the next `start` or `status` for a block that ended without one, never inside a hook. ActivityWatch keeps its own history, so a missed copy can be taken later.
- Window titles, page addresses and file paths are among the most private text goodall holds. They stay in the raw copy and are left out of `goodall export scout` until redaction is designed.
- ActivityWatch is not corroboration: anyone signed in to the eval account can edit or delete its data. It records the whole account all the time, Safari's private windows included, and the docs say so.
