# The administrator install creates the eval account and stages its first sign-in setup

Goodall is installed from an administrator macOS user account, and onboarding there offers to create the eval account, so that a person never has to find Users & Groups in System Settings or work out which pieces need an administrator. The order is: the administrator runs the install, which puts the system-level pieces in place; onboarding confirms everything an administrator must install is there; onboarding asks whether to create an eval account; on a yes, goodall creates it with macOS's `sysadminctl`, and the person chooses the account's name and password. Goodall checks first that no account has that name, creates the account as a standard one so the recording account stays low-privilege, and never passes the password on the command line, where other processes can briefly read it: `sysadminctl` asks for the password itself, with the terminal handed over to it (ADR 0011), so goodall never holds, stores or logs it. The rest of setup has to happen inside the new account, and it runs by itself the first time the person signs in there, explaining each step on screen. For that, the administrator install places a first-run script owned by root and read-only to everyone else, and a LaunchAgent in `/Library/LaunchAgents` that runs it at every sign-in, for every account. The script exits unless the current account is the eval account; on its first run there it completes setup, including starting a work block at sign-in (dedicated account mode, ADR 0021); it then notes that setup is done, so later sign-ins go straight to starting a work block. We rejected staging the scripts in `/Users/Shared`, the obvious place two accounts can both reach: every account on the Mac can write there, so anyone could alter a script before the eval account runs it. We rejected leaving account creation to the person as the only route, because part of goodall's audience is not at home in System Settings or a terminal; creating the account by hand stays possible. The cost we accept is that goodall now takes privileged actions on the Mac itself, which it did not before.

## Consequences

- This settles where goodall is installed so an eval account can run it: the administrator install puts it where every account on the Mac can run it and none but an administrator can change it. The exact place is chosen when this is built.
- Starting a work block at sign-in is on by default in an eval account. The workstream is the contributor's main workstream from local settings (ADR 0009), corrected afterwards with `goodall fixblock` if needed.
- The administrator step may also put a marker file straight into the new account's home folder, so the first-run script can tell the eval account from every other account without guessing by name.
- The first-run script cannot ask a question in the terminal (ADR 0012). The setup page is therefore answered in the administrator account, the administrator install stages the answers file where only root can change it, and first sign-in setup is the unattended path ADR 0012 already has. The answers file holds no secret values, by the existing check.
- `goodall doctor` gains read-only checks that the first-run script is owned by root and not writable by others, and that the LaunchAgent is present and points at it. `goodall teardown` removes both.
- Goodall runs each privileged command itself: it shows every planned change first, then goes through the runner with the terminal handed over, so macOS asks for the administrator password and goodall never sees it. Tests use the fake runner; no test creates a real account.
- The administrator install also places the LaunchAgent that starts the menu bar icon at sign-in (ADR 0024).
- The first sign-in part is a sketch until it has been run on a real Mac. Known unknowns: on a Mac with FileVault, whether the new account gets a secure token so it can unlock the disk at startup; and the first sign-in to a new account goes through macOS's own setup screens before any LaunchAgent runs.
