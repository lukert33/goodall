# An eval account is the default, and a person may record in their own account

Onboarding recommends an eval account and offers a clearly labeled second choice, own-account mode: recording work blocks in a macOS user account the person also uses for other things. The eval account stays the default because everything captured in it is eval activity, so there is little risk of recording personal work, and because it keeps the eval apart from the person's other files and sign-ins. We add own-account mode because a work block can be started and stopped, so a person can fairly ask to see what goodall shows about their own work with AI before making an account for it. Requiring an eval account for every use (ADR 0008's position) was rejected as too high a price for a first look. The risk own-account mode brings is consent drift: forgetting that a work block is active and capturing personal activity. Consent is therefore carried differently in the two. In an eval account goodall starts a work block when the person signs in, and the account itself is the consent boundary: signing in means recording. In own-account mode nothing starts unless the person starts it or set it up to start, and goodall adds safeguards against forgetting. In both, goodall shows a notification whenever a work block is started or stopped by something other than the person's own command, because that is the one moment the person does not already know. "Record" is the verb goodall uses with people for what it does, chosen because it is the clearest word for consent.

## Consequences

- ADR 0008 holds with one change: a macOS user account still holds at most one eval, but that account need no longer be an eval account. The eval account's rules (standard, non-admin, used for nothing else) apply to eval accounts only.
- A background start or stop is one made by signing in, by a schedule or script, or by goodall itself ending a work block. Each shows a notification. A start or stop the person typed shows none.
- Own-account mode has four safeguards: a recording indicator that stays visible while a work block is active, the notifications above, an optional automatic timeout, and an easy way to delete one work block's captured data. Deleting removes whole records and never edits one, so raw records that remain are still verbatim (ADR 0003).
- Onboarding says plainly that the data is local, in words like "Nothing is uploaded, ever, unless you export it." No automated upload is built or planned, metadata included (ADR 0017). That sentence has to be true of the record repo too, which goodall pushes to a remote today when one is set; `docs/open-questions/2026-11-26.md` (Q70) holds that conflict.
- Three existing behaviors assume an eval account and would capture or block personal work in a person's own account: the prompt gate refuses every Claude Code prompt outside a work block, ActivityWatch records the whole account all the time and goodall copies all of it (ADR 0016), and any agent session with a record inside a work block is copied whatever it was about (ADR 0019). Own-account mode is not built until each has an answer (Q72 to Q74).
- Notifications and the recording indicator are a second way goodall speaks to a person, beside the terminal. They go through the runner and the UI module like everything else (ADR 0011), and neither ever asks a question (ADR 0012).
