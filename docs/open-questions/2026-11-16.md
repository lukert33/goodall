## 1. Needs the owner

### Security

- **Q1. Upgrade uv on this machine.** The subagent that wrote CI reports advisory GHSA-hq85-5cpj-mr62: every uv below 0.13.4 ships a built-in certificate list that includes a compromised certificate authority. This machine has uv 0.11.28 (Homebrew). CI works around it by using the runner's system certificates. The lasting fix is `brew upgrade uv` and raising the `uv_build` range in `pyproject.toml` to match. Not independently verified. *Recommendation: upgrade, then one small pull request to raise the range.*
- **Q2. Approve the CI dependency rows.** `docs/DEPENDENCIES.md` now says "adopt" for the hosted runner image, `actions/checkout` (pinned by commit) and uv installed with a hash-checked pip install. Merging #9 was arguably that approval; confirm.
- **Q3. Hostnames in work block records.** A Mac's hostname often contains its owner's name. Should machine facts be flagged for redaction before release, or should the hostname not be recorded at all?

- **Q22. A telemetry line went missing once under load.** In CI on Linux, one of 40 simultaneous requests to the new receiver did not produce its line. GitHub cut the log off, so the cause was never seen. The subagent raised the listen backlog from 5 to 64 (its best guess) and the second run passed. For a recorder, an unexplained lost record deserves a proper look before the receiver is relied on. *Recommendation: reproduce it deliberately before the lifecycle ticket.*
- **Q23. Line breaks inside a telemetry request.** To keep one request per line, the receiver turns any line break between JSON tokens into a space: same length, same parsed value, but not byte-for-byte what was sent. Claude Code's own compact output is stored untouched. The change is not marked. Is that within "raw records stay verbatim" (ADR 0003), and does it want a short ADR?
- **Q24. Another program on the receiver's port.** With a fixed port, a different program could be listening there first and would receive the telemetry. The lifecycle ticket must check that goodall's receiver is the one listening. Confirm that a random port, read back from the receiver, is acceptable.

- **Q33. An env file other accounts can read.** It holds references, not secrets, but references name vaults and items. Ticket 7 makes loose permissions a warning with `chmod 600` as the next step. Should it be a failure, and is a `chmod` command a fair thing to show this audience?
- **Q34. Token-shaped values in the shared env file.** A value that looks like a long random token only warns, because the same test catches UUIDs and git hashes. A secret reference there fails. Is a warning the right strength?
- **Q35. Never print a secret reference.** The ticket said to name "the variable and the reference". The stricter rule adopted overnight: goodall's output names the variable and the line, never the reference, since a reference reveals a vault and item name. Confirm.

- **Q36. A healthy `goodall doctor` report always shows one "unverified" line.** Goodall can confirm that a referenced item exists in 1Password without reading anything secret, but it cannot confirm the FIELD exists without reading the value. So the field check is always reported as `unverified`, a new status that is neither pass nor FAIL. This contradicts ticket 8's first acceptance criterion, which expected a pass. The alternative closes the gap by having 1Password launch a do-nothing program with the secret injected, which reads the value. Is a permanent "unverified" line acceptable, or is that trade worth making?
- **Q37. Hand-test the secrets manager against real 1Password.** Nothing in ticket 8 was run against the real thing. To check by hand: (1) `op vault list` and `op item list` return no field values; (2) `op whoami` passes when signed in through the 1Password app; (3) `op` works when started with no terminal attached; (4) no Touch ID or approval prompt appears; (5) the exit codes for signed out and for an unreadable vault; (6) matching agrees with `op read` for archived items and duplicate names; (7) a large vault lists within ten seconds; (8) the sign-in next step is right.

- **Q41. Does an eval with no secrets need 1Password installed?** The independent review found `goodall doctor` fails such an eval because `op` is missing. The Foundations spec lists `op` as required; ADR 0006 says a secrets manager is needed only when a secret exists. Overnight choice: follow the ADR, so the check passes with a note when the env file holds no references. Confirm, and the spec line gets corrected.
- **Q42. Three ways a pasted secret was echoed back.** The review reproduced them by hand: a token ending in `=` read as an env-file variable name; a non-path value in a folder setting; and a secret typed where a setting name belongs. All three are being fixed in a follow-up pull request on top of the stack. The rule adopted: text taken from a settings or env file is quoted back only when it is known to be harmless (an absolute path, or a short name-like key). Otherwise the message gives the line number. Confirm the rule, since it makes some messages less specific.
- **Q43. Spec criteria knowingly not met.** "Healthy setup: every check passes" (see Q36) and "a missing item fails naming the reference" (see Q35) are contradicted on purpose. Three spec items were never ticketed and are not built: the append-only TOML writer, the plain refusal function for the hook path (the prompt gate ticket will build it), and starting and stopping a background program through the runner. Decide whether each becomes a ticket or leaves the spec.
- **Q44. An empty value in an env file is now refused.** This closes the `=`-padded token hole, but it also refuses a deliberately empty shared variable (`NAME=""`). Is there a real case for an empty variable in `.env.shared`?
- **Q45. `op://` anywhere in a shared value now fails.** There is one secret-reference rule now, and it is the looser one: `op://` found anywhere in a value, in any letter case. Confirm that strictness.
- **Q46. A token-shaped NAME in the shared env file only warns.** It matches how a token-shaped value is treated there (Q34); answer the two together.
- **Q47. The error for a relative `GOODALL_CONFIG_DIR` quotes that variable's value.** It is an environment variable, not a settings file, so the fix left it alone. Should the same no-echo rule apply?

## 2. Good enough to proceed, open to revision

### Settings and commands

- **R1.** The local settings file is `local-settings.toml` under `~/.config/goodall/` (ticket 2 briefly used `settings.toml`; corrected in ticket 3).
- **R2.** An empty `GOODALL_CONFIG_DIR` counts as unset; a relative one is refused.
- **R3.** Colour is off when `NO_COLOR` is set; width is clamped to 40 to 100 columns and fixed at 80 when output is not a terminal.
- **R4.** The `dry-run` help text now reads "Rehearse a whole work block without recording a real eval".
- **R5.** "session" survives only in tests that check the old names are gone, in Claude Code's own `SessionStart` event names, and in the Beads-managed block of `AGENTS.md`.

### CI

- **R6.** CI runs on `ubuntu-24.04`, not macOS. The tests need only git, sh and Python, but macOS-specific behaviour is not exercised.
- **R7.** Only the Linux x86_64 uv wheel hash is listed, so an ARM runner would fail to install uv.
- **R8.** A 15-minute job timeout; the gates run one after another.

### Merged-branch hook

- **R9.** A branch switch counts only when joined to the commit by `&&`. A newly created branch is still checked with GitHub. Known gaps: checking out a remote-only branch, `cd` into a subfolder after a switch, and a single `&`.

### Transcripts and labels

- **R10.** Rejections are found by their text, not by `toolDenialKind`. Blank lines are skipped. `userType` is ignored because it is always "external".
- **R11.** The list of known entry types is drawn from this machine's transcripts.
- **R12.** `between_turns` interruptions are never produced; the transcript has no signal for them.
- **R13.** Each entry gets one actor label, its primary producer, plus a `mixed` flag. Whether an entry is mixed is fixed per rule.
- **R14.** Subagent instructions are labelled `ai`.
- **R15.** Two docs files: `docs/human-action-rules.md` and `docs/actor-label-rules.md`.

### Records

- **R16.** The metadata header is TOML between `+++` lines.
- **R17.** File names are UTC time, contributor id and eight random hex characters.
- **R18.** A running work block has a record with no end; ids use `[a-z0-9-]`, at most 64 characters; timestamps are whole seconds; one flat folder per record type; a body containing an email address is refused.

### Telemetry receiver

- **R20.** The request body is capped at 20 MiB, the Collector's default.
- **R21.** The `Host` header must be exactly `127.0.0.1:<port>`; `localhost` is refused. Any request carrying an `Origin` header is refused, and no CORS headers are ever sent.
- **R22.** A write failure answers 503 so the sender retries. The directory must already exist. Files are created readable by the owner only, and a symbolic link at a file's name is refused.
- **R23.** Each write is forced to disk before the request is answered (using macOS's full sync).
- **R24.** Run as a process, the receiver prints its port as one JSON line directly, since it has no UI module to go through.

### Settings reader

- **R25.** `goodall status --json` always has the shape `{"work_block_active": ..., "failures": [...]}`.
- **R26.** Every problem in a settings file is reported at once; a schema version that is too new reports only "upgrade goodall".
- **R27.** Values from a settings file are never echoed back, only folders, because a misplaced value could be a pasted secret.
- **R28.** `~someone/` and relative folders are refused. Unknown keys get a "did you mean" suggestion. The log directory must be writable, or status reports "not recording".

### Eval config reader

- **R29.** Workstreams and intervention categories follow the same naming rule as contributor ids: lowercase letters, digits and hyphens.
- **R30.** `description` is required and may not be empty. The eval config needs at least one workstream, category, contributor and scope entry.
- **R31.** A repository identity may have more than three parts (for GitLab subgroups); a trailing `.git` is refused; case is not normalised.
- **R32.** The email check is deliberately broad, so a `git@host:` repository address trips it as well as the repository check. Only `op://` is recognised as a secret reference.
- **R33.** `goodall status --json` adds `eval` and `contributor`, which are null whenever there are failures.

### Doctor

- **R34.** Only the code that runs the checks can skip one, so a skip always sits beside a failure in the same report. The exit code is 1 only when a check failed; warnings alone do not fail it.
- **R35.** The whole report goes to standard output, failures included. (The spec says failures go to standard error; for a report it is one document.)
- **R36.** The report leaves out each failure's "why"; it is still in `--json`.
- **R37.** The seven settings checks sit in one "Settings" group with ids like `settings.local_settings_valid`.
- **R38.** The JSON document's version key is `schema_version`, matching the settings files.

### Runner gateway and tool checks

- **R39.** `sudo` and `wheel` count as administrator groups alongside `admin`, so the account check behaves on Linux too.
- **R40.** The fake runner ships inside the package (`goodall.fake_runner`), so tests and later tickets can import it.
- **R41.** "Only the runner starts programs" is enforced by a lint rule banning `subprocess` and its relatives, with three stated exemptions: the runner, the tests, and the merged-branch hook. It does not catch deliberate tricks through `importlib`.
- **R42.** The secrets manager's install check waits for valid local settings, since those name the manager. The git-repository check sits in its own "Record repo" group.
- **R43.** The runner does not strip `GIT_*` variables from git's environment; the record repo operations must protect themselves.

### Record repo operations

- **R44.** A rejected push is handled by fetching, combining with a merge commit (never a rebase, never a forced push) and retrying, up to three times. It merges only when no tracked file has uncommitted changes.
- **R45.** A push goes to the branch's upstream, else to `origin` under the same branch name. Timeouts are 30 seconds for push and fetch and 60 for commit and merge.
- **R46.** The commit message reads `Add journal entry <id>`, with a body naming the contributor. The author is git's configured identity; with none configured, goodall refuses before writing anything. No AI co-author trailer: goodall the tool makes these commits.
- **R47.** If the contributor's own hook or signing setup refuses a commit, the written file is kept and the problem reported.
- **R48.** Not verified against a real hosted remote, a real authentication failure, an SSH key with a passphrase, or commit signing.

### Env files

- **R49.** A well-formed 1Password reference is `op://vault/item/field` or `op://vault/item/section/field`, lowercase `op://`, each part using letters, digits, space, underscore, dot and hyphen. A `?query` is refused.
- **R50.** `export NAME=value` is refused with its own message. An unquoted value containing spaces is refused. Quotes are removed with no escape handling. A name set twice in one file is a problem.
- **R51.** No message ever repeats what is written on a line, including an invalid name.
- **R52.** A passing check can carry a note, shown in the report and as `"note"` in `--json`.
- **R53.** Not verified: whether 1Password's own `op run --env-file` reads these lines the same way goodall does.

### Secrets manager

- **R54.** Goodall runs only `op whoami` (output discarded), `op vault list` and `op item list` (ids and names kept in memory, never printed). It never runs `op item get`, `op read`, `op inject` or `op run`; a test enforces that.
- **R55.** A new `unverified` status. The report's status column widens from 6 to 12 characters, and the `--json` summary gains an `unverified` count.
- **R56.** With no references in the env file, the sign-in check asks 1Password nothing and passes with a note. An `op whoami` that times out is a failure, not "unverified".
- **R57.** Item names match case-insensitively, as 1Password documents; duplicate names give "unverified".

### Journal and intervene

- **R58.** Text comes from an argument, from standard input, or from `--file` (for something written in TextEdit). Empty text is refused. Text is capped at 100,000 characters.
- **R59.** `--occurred-at` is read in this Mac's local time; "14:05" means the most recent 14:05; a date alone or a future time is refused.
- **R60.** Every usage mistake exits 2. Category and decision values are never echoed back. Examples in error messages are complete commands, with no placeholders.
- **R61.** The intervention's "question outcome" field is not offered as a flag.

### Work blocks

- **R73.** The running block is a marker file, `work-blocks/active-work-block.json` in the log directory, readable only by this account, created atomically and never rewritten. Heartbeats are appended to `work-blocks/heartbeats/<id>.jsonl`.
- **R74.** An unknown `--workstream` exits 2 without echoing what was typed. `start` and `stop` have no `--json`.
- **R75.** `goodall stop` the morning after a forgotten block closes it as inferred and exits 0. A heartbeat never revives an overdue block.
- **R76.** A journal entry is stamped with the work block only while one is active; an intervention dated before the block began is not stamped.
- **R77.** The status JSON gains `work_block`, `ended_work_blocks` and `warnings`.
- **R78.** Not verified: the fallback for disks without hard links, the real `claude --version` format, two `stop` commands racing, a drive truly unplugged (simulated by renaming the folder).
- **R79.** New terms not yet in the glossary: marker, overdue, idle limit, waiting record, damaged marker.

### Prompt gate hook

- **R80.** The command is `goodall hook <event>` with Claude Code's JSON on standard input. The event is named on the command line so the gate still refuses when the input cannot be read.
- **R81.** `goodall hook` skips the normal command parser, so it adds about 23 ms to each prompt on this Mac (34 ms in all).
- **R82.** Six refusal messages, each ending with what to do; none names the log directory or any settings value. An overdue work block gets the same message as no work block.
- **R83.** PostToolUse, Stop, SessionEnd and SessionStart record a heartbeat, print nothing and always exit 0.
- **R84.** The documented snippet uses a full path to `goodall`, since Claude Code's PATH may differ from the terminal's.

### Transcript sync

- **R85.** A copy is skipped when size and modification time match the source. Anything else is copied whole to a temporary file and renamed into place, then checked to begin with every byte of the earlier copy.
- **R86.** A copy that fails inside a hook stays silent there, is noted in `transcript-sync/failed-copies.jsonl`, and `goodall status` reports it.
- **R87.** `goodall start`, `stop` and `status` sweep for anything the hooks missed and say so in one sentence only when something was copied.
- **R88.** A per-session lock (waits at most ten seconds) stops parallel hooks racing. Temporary files older than ten minutes are removed.
- **R89.** A failing heartbeat no longer skips the copy.
- **R90.** Measured on this Mac: nothing added when the transcript is unchanged; about 3 ms for a 5 MB transcript that grew, about 15 ms for 50 MB.
- **R91.** Not verified: whether Claude Code rewrites `.meta.json` files (each rewrite would file a superseded copy); log directories on exFAT or a network drive.

## 3. Well decided, for the record

- `goodall session` is removed outright, with no alias.
